## 真实数据库与 HTTP 集成

在已核实的 `postgrese` 数据库创建任务专用临时 schema `chemistry_refactor_verification_01a183a2`，只在该 schema 应用三项迁移并建立测试账号、数据库会话和文章。14 张应用表均已启用 RLS。

最终 13 组 HTTP 检查全部通过：

- 数据库会话读取、管理员页面及普通用户和匿名访问保护。
- 管理员创建、修改和删除文章；双语正文和翻译更新保持正确。
- 前台目录与阅读页读取已发布数据库内容；兼容路径及旧编码 slug。
- 普通用户及匿名用户无法调用管理员写接口。
- 无效 JSON、非法 slug、重复 slug、跨站请求均被拒绝。
- 进度写入、重复完成请求保持同一记录与时间戳、账户页读取真实进度。
- 私有文章及草稿不会通过公开阅读、文件回退或其他语言泄露正文。
- Markdown 预览保留数学内容，过滤脚本与危险链接。
- 未配置 Storage 时上传返回明确失败；不会伪造成功。
- 内置文章不能通过删除或改名移除数据库覆盖；独立笔记仍可改名和删除。

联调修复了一个真实问题：Next.js 的内部 URL 使用 `localhost`，会使合法的 `127.0.0.1` 浏览器请求被原来的 Origin 检查误拒绝。当前检查校验请求 Host 和单一的 HTTP/HTTPS 代理协议，继续拒绝外部 Origin 及格式错误的头字段。

这次验证读取了真实数据库会话，未执行真实 Google OAuth 授权交换。Storage 的对象上传、失败补偿和稳定 URL 有单元测试；未执行真实云端对象上传或跨部署读取。

- 确认原应用仍为旧角色枚举，因此没有直接把新版登录连接到未升级的 `public`。
- 在同一个已确认的 `postgrese` 数据库建立持久开发 schema `chemistry_development`，应用三项迁移并导入两章双语课程。
- 写入被 Git 忽略、权限为 `0600` 的 `.env.local`，仅覆盖本地数据库目标、origin 和登录模式；原 `.env` 保留。
- 本机预览只监听 `127.0.0.1`，使用现有 Google 配置及真实数据库，浏览器和 `NEXTAUTH_URL` 均为 `http://localhost:3000`。
- `/api/auth/providers`、`/api/auth/session` 和 `/login` 返回 200；Google provider 与登录按钮已启用，未配置提示已消失。
- 浏览器点击登录后正常进入 Google 的 “Physical Chem” 登录页，需要用户本人完成登录及授权。
- 建立开发区域前后，既有 `public` 的用户、OAuth 账户、会话聚合数量保持一致，均为 0；未升级其表结构。
